# TgGroupRobot 服务修复实施与运行恢复设计

> 版本：v1.0
> 日期：2026-10-10（Asia/Shanghai）
> 状态：候选实现及本地验证完成；三类隔离数据库已验证至 0014，尚未生产发布
> 实际证据：[验收记录](../product/2026-10-10-service-repair-acceptance.md)
> 产品约束：[服务修复与交互统一 PRD](../product/2026-10-10-service-repair-prd.md)

## 1. 实施原则

先修当前链路，再迁移公共契约；保留现有功能域、领域数据和可靠执行器。一个功能迁移后仅有一个执行实现，旧入口负责转译，不维护两套业务逻辑。

本设计中的契约为实现依据。当前精确字段以 ORM、Alembic 0008–0014 和数据库设计增量为准；已在隔离数据库执行迁移，生产尚未变更。本文设计目标与实际验收结果分别维护。

## 2. 统一请求与功能注册

功能描述保留静态元数据与业务适配器两部分，禁止成为承载所有业务参数的大对象。

| 描述项 | 内容 |
|---|---|
| identity | 稳定 feature_id、所属分类、唯一主入口、兼容别名 |
| capability | 角色/群策略、必要机器人权限、不可用原因 |
| route_specs | 公开命令、回调模式、输入状态及其唯一所有者 |
| handlers | 页面处理、业务动作、输入处理的显式接口 |
| adapters | 配置读写、消息编辑、列表查询等可选适配器 |
| acceptance | 需求编号、验收场景、功能证据条目 |

请求归一后的基本信息为 actor_user_id、target_chat_id、feature_id、action、entity_id、navigation_context、operation_id。业务字段放在有类型的 action payload 中。目标群只能来自经过校验的原页面/对象/深链，不能被“当前选择群”覆盖。

实施落点：

- backend/app/router_registry.py 保持装配入口；各功能贡献自己的描述与处理器。
- backend/features/admin/runtime.py 的旧分发表先修正关键字传参，再由显式适配接口逐域替换。
- private_config_registry 的状态 key 必须检测重复注册；启动/验证阶段发现两个所有者直接失败，不让后注册覆盖前注册。
- callback 与 ConversationHandler 的优先级必须实测；同一 Update 只能执行一次业务动作，早注册的通用前缀不得吞掉必要的退出状态处理。
- 静态入口检查覆盖 renderer 生成的按钮和动态实体按钮；运行测试保留真实分发函数，不能只断言正则匹配。

## 3. 导航与编辑会话

### 3.1 导航信息

NavigationContext 记录目标群、功能、资源、来源页面、返回目标、筛选/排序/页码或游标、页面版本。页面生成时确定目标身份；点击时重新校验权限与对象归属。

来源记录不放任意可执行 handler 名称。返回目标使用注册的页面标识及结构化参数；来源失效时回到原群的功能列表。回调长度、字符编码和最大参数样本在生成器测试中按所用 Telegram SDK 的约束检查；必要时使用服务端短 token，不在回调中塞完整草稿。

### 3.2 编辑状态

继续以 ConversationStateService 为统一入口，但将导航、输入指针和草稿独立建模。当前 (chat_id, user_id) 唯一记录与 selected_chat 写法不能直接承载未经协调的多份状态。

建议在现有私聊状态记录中使用带版本的 envelope 保存 navigation、active_input 和草稿引用/内容；活跃输入兼容旧 state_type 的解析由统一适配层负责。若草稿规模需要独立存储，再以显式迁移增加领域无关的 UI 草稿表，不为此引入新工作流引擎。

无论物理存储选择哪一种，必须满足：

1. 草稿键包含用户、群、功能和对象/新建草稿 ID；不会因切群被覆盖。
2. 开始、更新、暂停、放弃和提交均经同一状态服务；成功切群原子更新 navigation 并解除旧 active_input，保留原群草稿；失败不切换。清理输入不删除导航，打开旧页面不自动激活输入。
3. 每个私聊用户只有一个 active_input；没有 active_input 时不把普通文本送入配置处理器。
4. 草稿包含 base_revision、draft_revision、修改时间和过期时间。写入采用原子更新或行锁，避免导航更新丢掉同时写入的草稿。
5. 旧群作用域输入状态只在身份明确时按读取兼容迁移；不能识别的状态退出输入并解释原因，不猜测写入对象。
6. 保存校验配置版本；冲突不强行覆盖。保存成功后读取正式配置生成结果页，避免只显示内存草稿。
7. 新格式必须被回退目标理解；不兼容时使用已演练的状态转换，列出受影响草稿，不通过清空全库状态回退。

配置正文与按钮采用草稿保存模式；即时开关保留为独立动作。这是对当前部分按钮编辑即写正式配置的明确行为修改，必须纳入迁移与测试。

启用新 envelope 前，所有旧状态写入、clear、TTL 清理与 selected_chat 入口必须先经兼容适配，保证不会整体覆盖或删除新格式。旧群作用域记录完成迁移后，在同一事务内标为已迁移或解除其输入效力，防止 fallback 再次接收。混合版本节点不得同时用不兼容的状态写法处理同一用户。

旧私聊状态与旧群作用域状态同时存在且无法确定输入归属时，保留可恢复草稿并提示用户选择，不猜测 active_input。迁移须可重复执行且始终至多保留一个 active_input；验证覆盖旧私聊状态、旧群状态、两者冲突、旧 clear、TTL 清理和迁移后重启。

## 4. 公共组件迁移

| 组件 | 沿用的基础 | 本轮需要收敛的内容 |
|---|---|---|
| 页面导航 | ChatResolver、现有页面与群选择 | 目标身份、来源、空态、返回、权限原因 |
| 编辑器 | ConversationStateService、message_config_panel | 独立草稿、退出输入、冲突、保存结果 |
| 按钮编辑 | ButtonLayoutEditorService、button_input | 可视化为默认入口，文本/JSON 作为高级导入 |
| 列表 | KeyboardBuilder/分页辅助与现有查询服务 | 保留一套公共分页契约，移除迁移模块的平行算法 |
| 消息输出 | PublishService、MessageHelper | 文字/媒体一致渲染、失败分类、结果可恢复 |
| 权限 | PermissionPolicyService | 展示与执行同源；提交时再次校验 |

消息编辑适配器提供 load、validate、save、render_preview、back_target。公共层只依赖协议与数据结构，业务模块提供实现；从 shared 中移出对业务私有 handler 的直接导入和反向调用。

迁移顺序：命令配置/群选择/商城列表验证基础交互；自动回复与轮播消息验证有实体的消息适配；欢迎、邀请、定时消息、强制订阅、频道同步接入相同编辑契约；最后覆盖活动、车库等页面并清理失去调用者的公共抽象。

底部按钮和自动回复动作保留各自允许的按钮类型。预览中的动作按钮绑定预览处理，不能触发正式签到、扣分或处罚。定时与广告的预览不生成正式 occurrence/delivery。

## 5. 商城一致性与数据增量

### 5.1 兑换意图

兑换意图至少持久化：唯一 ID、目标群、购买者、商品、数量、交易条件快照/版本、有效期、状态、关联订单。确认 token 只能由绑定用户消费，并在服务端重新校验目标群与参与资格。

状态为 pending / consumed / cancelled / expired。同一意图只产生一个订单，以数据库唯一约束保证；过期或取消不会形成订单。已消费意图再次访问返回原订单，不再次扣分。

### 5.2 提交边界

统一兑换事务执行顺序：

1. 锁定或原子认领兑换意图；已消费则返回原结果。
2. 在与关闭商城操作一致的锁/版本协议下检查当前商城 enabled。
3. 按固定锁顺序读取商品、个人限购与积分账户，检查归属、上架、库存、交易条件和余额。
4. 原子扣分、减库存、生成订单及不可变商品/发放快照，标记意图已消费，写入对应流水与通知待投递记录。
5. 提交事务后展示结果，异步发送通知。外部发送不得放在持有库存/账户锁的事务中。

关闭商城与兑换必须共享配置行的并发规则，避免“检查时开启、关闭已提交后仍新建订单”的竞态。商品限购的读取与写入不得在并发意图间失去一致性。取消、退款和发放按订单状态条件更新与幂等键执行，遵循已有退款与库存恢复业务语义。

### 5.3 订单与发放数据

在既有订单模型上增量保存：兑换意图关联、商品/价格/说明快照、成交时发放人员、当前责任人、改派日志、人工发放说明与时间。已有订单不重算扣分、不回写当前商品价格。

旧订单无法还原的历史快照标记“历史信息未记录”，禁止用商品当前内容伪造原交易承诺。已有 fulfilled 订单沿用内部状态，展示“已人工标记发放”，不批量伪造交付凭据。

普通发放人员仅能处理明确分配给自己的订单；这是一项订单级权限，不继承群管理权限。离群或分配被撤销后拒绝处理，管理员可显式接管。取消/退款保留现有管理员权限边界。

### 5.4 通知投递

商城新增通知记录复用 backend/platform/delivery 的状态与重试语义，并在商城领域实现接收者、载荷和处理逻辑；不新建第二套全局 Outbox 框架。记录至少包含订单、接收者、通知类型/版本、唯一投递键、状态、尝试与 message_id。

状态遵循 pending / processing / retryable_failed / succeeded / permanent_failed / uncertain / cancelled。订单与待通知记录在同一事务落库；明确失败可退避重试，发送开始后的不确定结果进入 uncertain，禁止自动重发。通知状态不会自动把订单改为 fulfilled。

没有可达私聊或通知永久失败时，管理员待处理列表显示异常与接管入口。重试只操作该通知记录，不能重新执行兑换。改派在同一事务内更新责任人版本、取消旧人员尚未开始发送的通知并新增对应通知版本。worker 认领后、发送前再次校验当前分配；已在途或未知结果不能伪造撤回成功，保留事实且不再自动向旧人员重试。旧按钮始终按当前分配校验。

## 6. 发布预览与错误反馈

渲染器输出内容快照，预览与正式发布使用同一快照。预览目标为操作人的私聊；正式操作的目标群来自已确认上下文。

已有定时、广告、转发使用现有执行记录。竞猜/拍卖等即时发布增加或补全领域内的发布意图及结果关联，稳定标识绑定一次发布，不将点击重试变成新建活动。明确失败可修复重试；未知结果保留待核实状态。媒体分多条发送时逐条记录发送身份与结果，避免部分成功后整组重发。

活动可参与资格须同时满足原业务时限/状态和已确认发布。发送前失败、发送后结果落库失败都不能因存在活动行而开放参与；明确成功或人工核实同一消息后关联并激活。核实时已超过原截止时间的活动按原规则结束，不自动延长。

操作结果至少区分 unchanged、saved、denied、validation_failed、render_failed、failed、unknown；对应的业务执行仍沿用领域状态。编辑管理消息失败时允许重新发送管理面板，不能借此重新执行扣分、发布或处罚。

callback answer 只负责及时确认收到。之后的成功/失败通过消息编辑、补发管理面板或持久化待告知结果呈现。用户文案不包含原始 SQL、路径或内部异常；日志通过 operation_id 与业务对象关联。

## 7. 历史协议与迁移

| 旧入口 | 兼容行为 |
|---|---|
| 明确绑定群的旧导航 | 校验后进入同一功能的新页面，保留目标群 |
| 群设置 | 进入系统管理分类，不返回原首页 |
| 旧频道同步/车库转发 | 归一到同一配置页面，保留原对象绑定 |
| 只有 toggle 的旧开关 | 刷新到显式启停页，让用户重新选择 |
| 旧 mall:redeem | 打开商品详情/重新确认，不直接扣分 |
| 缺少群身份的私聊旧写入 | 选群后重新展示操作，不自动补当前群执行 |
| 已删除对象/无法识别状态 | 明确说明并提供同群功能列表 |

兼容层只转译，不生成旧协议。移除兼容代码前需检查回调使用情况和旧消息可达性；不能假定旧 Telegram 消息会在固定天数后全部消失。

新增字段/表先做兼容性扩展，业务读写迁移完成前不删除原字段。每次数据库变更更新 Alembic、Schema Gate 和设计文档，验证空库、现有库升级及降级限制。

## 8. 运行观察与恢复

审计至少记录：版本、operation_id、Update/callback 标识、actor、target_chat、feature/action、对象、请求结果、配置提交结果、页面呈现结果、投递结果。业务文本只记录必要摘要，避免在日志中复制完整用户内容。

需要能区分以下问题：

- 按钮未注册或参数错误；
- 权限拒绝、配置未完成或功能关闭；
- 输入状态过期/冲突；
- 数据写入失败；
- 数据已保存但页面刷新失败；
- 执行明确失败、结果未知、通知未到达。

建立按功能统计的入口处理错误、页面刷新失败、版本冲突和投递状态计数。任何跨群写入、重复扣分或意图重复创建均为停止该功能推广的阻断项；不设置未经采样验证的生产成功率承诺。

## 9. 发布与回退

1. M0 先形成修复后的安全基线；后续导航回退不能回到已知管理分发失效或商城开关可绕过的版本。
2. M1/M2 先在专用验收群启用迁移页面，保留明确的版本/功能配置。不得让新旧 handler 对同一次更新双重执行。
3. 每次推广先记录代码 SHA、镜像/制品身份、数据库 revision、功能启用范围，再执行 PRD 的对应验收场景。
4. 应用回退与数据库回退分别评估。通常回退页面与适配实现，保留发布后新增的订单、积分流水和执行记录；不能常规恢复全库快照抹掉新业务。
5. 若旧代码无法读取新状态/订单字段，使用经过演练的兼容版本或前向修复；没有兼容验证时不得宣称“可一键回滚”。
6. 失败恢复入口区分“重试明确失败”“重新打开结果”“核实未知结果”“人工确认重放”。不确定重放继续要求明确二次确认并留来源关联。

回退演练还必须证明未完成通知/发布意图有人消费，以及在途租约、已发送未收尾和 uncertain 记录能够继续核实。停旧 worker、等待或隔离在途操作、再启兼容 worker，不能同时双重认领或把未知结果重置成 pending。若回退版本没有新任务消费能力，应保留兼容 worker 或采用前向修复，不能只回退 Web/菜单后停止处理订单。

版本切换前先停止新增相应认领，记录并核对 pending、processing、uncertain 数量及在途租约；切换后核对去向与消费能力。回退演练须包含未完成通知、在途发布和未知结果，不能只在空队列上验证启动成功。

真实验收完成前，发布记录分别注明“制品已部署”“进程健康”“目标功能验收通过”，禁止合并成一个完成标记。实际发布按独立发布任务执行。

## 10. 验证分层与交付物

| 层次 | 必须验证 | 不能替代的证据 |
|---|---|---|
| 静态契约 | 描述、菜单、路由、状态无重复所有者；调用签名一致 | 真实点击执行 |
| 真实路由集成 | 实际生成按钮 → Update → 注册路由 → 权限/状态 → 业务服务 | Telegram 实际展示 |
| 隔离 PostgreSQL | 事务、幂等、并发、版本冲突、重启恢复、迁移 | 生产数据库已经升级 |
| Telegram 专用群 | 同版本、同群、同用户/对象的完整操作与结果 | 所有线上用户均正常 |
| 运行回读 | 配置、订单、余额/库存、消息或执行记录对应 | 用户实际收到实物等线下交付 |

集成测试不得替换受验收的 router、目标群解析或分发函数。数据库只使用隔离测试库，不能因默认环境变量误连生产。Telegram 网络替身用于错误注入，现场验收另行记录。

文档交付物为本 PRD、配套设计、入口索引和纠正后的问题/功能基线。本轮实现及证据已记录于验收记录；旧二进制回退、全量 Telegram 及生产发布观察仍未完成，不预填“通过”。


## 下游调用门禁补充

可静态解析的函数、转导出和唯一 mixin 方法使用 scripts/check_call_contracts.py 验证参数契约；发布 checks 在质量检查后执行。mypy 全局启用 call-arg，Settings 环境变量构造例外限制于配置模块。入群保护、反垃圾用户身份、验证解禁与状态写入使用实际关键字契约；广告历史统一复用安全页面编辑。动态调用仍要求注册签名及实际 Application/DB 回归，不将静态检查替代业务证明。


## 2026-10-15 通用管理实施补充

## v0.7 剩余通用能力实现

新增asan私聊管理路由，执行前及解除前重新复核当前策略、机器人权限和目标状态。移除联盟池/退出只停止传播，不自动解除。既有/未知处罚不取得所有权；解除后本池版本本群不再立即处罚。附加动作恢复只处理已确认消息ID；未确认消息不造链接、不盲目重发。导入/克隆复制所选配置而不复制目标运行状态、同意或余额。详见[本轮实施记录](../product/2026-10-15-remaining-general-features.md)。未部署或执行真实Telegram测试。

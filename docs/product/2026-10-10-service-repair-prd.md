## 1. 目标与交付边界

本轮解决三个用户问题：功能入口难找且重复、按钮背后的流程不完整、相同操作在不同功能中需要不同用法。先恢复可用性，再统一导航和交互，最后补齐已确认的业务缺口。保留已有群配置、积分、活动和历史记录，沿用现有业务服务逐步迁移。

最终应达到：

1. 每个展示的功能入口有可执行路径；没有权限、未配置、功能关闭、对象已删除时都有明确说明和出口。
2. 管理员从当前群首页进入任一功能首页，最多经过“分类 → 功能”两次点击；复杂操作的步骤按实际业务保留。
3. 同类列表、开关、输入、消息编辑、保存和返回遵循同一规则。
4. 配置能保存、运行时消费配置、用户看到结果分别验收；不以按钮存在或单元测试通过代替功能完成。
5. 修复不得造成跨群写入、重复扣分、丢失草稿或自动重复执行结果未知的业务操作。

### 1.1 本轮范围

| 范围 | 本轮交付 |
|---|---|
| 可用性 | 管理分发、/admin、错误反馈、商城关闭限制 |
| 导航 | 六类管理入口、功能主入口归属、统一选群、旧按钮兼容 |
| 公共交互 | 权限展示、返回与草稿、显式启停、分页、消息与按钮编辑 |
| 业务补全 | 商城详情/确认/指定人员通知、竞猜封面、拍卖图片输入、已确认的列表缺口 |
| 工程治理 | 注册契约、公共层依赖、真实路由测试、功能证据台账、分阶段上线与回退 |

本轮不新增收费门禁，不重写抽奖/游戏/竞猜结算算法，不重建全部数据库，不将群级管理迁到 Web 后台。商城本轮实现“通知后人工发放”，自动卡密、实物物流、第三方自动履约保留为后续能力，不以本轮交付代替。

现有定时消息、广告、验证超时和频道转发的可靠执行记录与恢复语义继续保留。导航或发布组件迁移不得绕开这些领域已有的执行实例、租约和不确定结果处理。

## 3. 用户角色与使用边界

| 角色 | 允许的操作 | 约束 |
|---|---|---|
| 群主/满足群策略的管理员 | 在私聊配置对应群、管理业务和恢复失败操作 | 每次写入重新校验群策略与对象归属 |
| 不满足群策略的管理员 | 查看权限说明、重新检查、选择其他群 | 不展示为“可配置”，不允许借旧按钮写入 |
| 普通群成员 | 参与已开启业务、查看自己的兑换结果 | 权限、功能开关和参与资格在执行时重新校验 |
| 指定商城发放人员 | 查看本群分配给自己的订单，填写发放说明并标记发放 | 不因此获得全部群管理、改价、加减积分或退款权限 |
| 平台管理员 | 沿用现有平台管理与运维权限 | 不因本轮导航调整改变现有角色边界 |

“可进入页面”“可以修改配置”“具备执行所需机器人权限”分别显示。机器人缺少某项权限时，允许管理员查看配置与修复指引，不将配置已保存显示为业务已生效。

## 4. 导航与页面设计

### N01 六类管理入口

群管理首页保留六个分类按钮，两列排列。页头显示当前群名和管理资格；页脚为“切换群”“刷新页面”。不再平铺 39 个功能按钮。健康检查与统计摘要只能展示真实读取的数据，读取失败显示“暂时无法获取”。

~~~text
当前群：示例群
管理资格：可配置

[ 群安全      ] [ 消息运营    ]
[ 积分与增长  ] [ 活动互动    ]
[ 车库业务    ] [ 系统管理    ]

[ 切换群      ] [ 刷新页面    ]
~~~

| 分类 | 功能主入口与子功能 |
|---|---|
| 群安全 | 进群欢迎、进群验证、新成员限制、垃圾防护、惩罚策略、删除提示、夜间管控、改名监控、强制订阅、联盟功能；违禁词、防刷屏、白名单归入垃圾防护 |
| 消息运营 | 轮播广告、自动回复、定时消息、频道同步、底部按钮、快捷发布 |
| 积分与增长 | 主积分、自定义积分、积分等级、积分商城、邀请链接、账号继承 |
| 活动互动 | 抽奖、接龙、拍卖、游戏、竞猜、促活工具 |
| 车库业务 | 车库认证、老师搜索、车评系统；老师资料、附近搜索等既有子功能按现有角色保留 |
| 系统管理 | 命令配置、健康检查、群组统计、导入设置、克隆设置、管理权限、服务状态 |

当前 39 个入口中，37 个功能主入口全部纳入上述分类；“群设置”改为系统管理分类入口，“切换群”改为全局导航。接龙已有实现但未出现在当前 39 项首页中，本轮补上活动分类入口，不作为新业务开发。

命名统一：原“强制关注”在管理界面改称“强制订阅”，原“炸号继承”改称“账号继承”，原“续费订阅”入口显示“服务状态”。功能标识、数据与旧回调保持兼容。当前付费限制关闭，服务状态页明确“当前功能开放”，不新增购买操作。既有套餐/有效期信息与卡密核销能力保留，继续按原权限与一次核销规则执行；旧 renew/sub/adm 续费入口接入同一处理链，不因改名恢复收费门禁。

每个功能只有一个分类主入口。允许“垃圾防护 → 违禁词”“活动 → 积分设置”等上下文快捷入口，但必须复用同一功能页面与服务，并保存返回来源。频道同步和车库转发若指向同一能力，统一在消息运营配置，车库侧仅保留有业务上下文的快捷入口。

功能首页固定展示群名、功能名称、核心操作和返回；开关、配置完整性、必要权限及最近执行状态按适用性展示。健康检查、统计等没有业务开关的页面不虚构“已开启”。启用状态与最近执行状态分开，例如“已开启；最近一次发送失败”，不得用一个绿色图标替代两种事实。

### N02 统一选群与权限

1. 带业务 payload 的 /start 优先处理原有邀请中转、老师定位、老师自助定位、车评提交等深链，并保持原业务资格校验。无 payload 时先识别角色：认证老师保留资料维护入口，指定发放人员保留“我的待发放订单”，不受是否有可管理群限制。管理员的 /start 与 /admin 复用同一个群管理区域：无可管理群时展示接入指引和刷新；只有一个时进入该群；多个群优先进入仍有权限的已选群，否则显示选择列表。兼具角色的用户同时保留对应自助入口。
2. 群内 /admin 校验管理员资格后，提供绑定该群的私聊管理链接，不在群内展开整套配置。私聊打开链接时再次校验资格。
3. 群选择、页面可操作状态、按钮处理、文本提交使用同一权限决策；不满足策略时解释具体条件，保留“重新检查/切换群”。
4. 选群列表统一分页、当前群标识和刷新；空态始终保留刷新，操作失败不清空全部导航。
5. 页面和输入均绑定原目标群。切换到 B 群后点击旧 A 群页面，只能重新校验并打开 A 群上下文，不得将原操作套用到 B 群。
6. 私聊旧按钮缺少可信群标识时，进入选群并重新展示操作；不得凭当前选中群补齐一个有副作用的旧操作。
7. 权限撤销、机器人离群、对象删除均阻止提交，保留可解释的返回路径；恢复权限后由用户重新提交。

### N03 返回与编辑状态

一个私聊同一时刻仅有一个正在接收输入的编辑流程。导航状态、草稿和输入接收状态分别管理；切群不能覆盖草稿内容或留下与新群不匹配的旧 state_type。

| 用户动作 | 输入状态 | 草稿与正式配置 | 返回位置 |
|---|---|---|---|
| 返回上一级 | 退出当前输入接收 | 保留草稿，不提交 | 原列表页/详情页，保留筛选、页码 |
| 返回管理首页 | 退出当前输入接收 | 保留草稿 | 当前页面绑定群的首页 |
| 切换群 | 挂起原群输入 | 保留原群草稿 | 校验通过后的目标群 |
| 退出编辑或 /cancel | 退出当前输入接收 | 保留草稿；提示“已退出，草稿已保留” | 原功能页 |
| 放弃修改/取消本次修改 | 退出当前输入接收 | 经明确确认丢弃未保存内容，恢复已保存版本 | 原对象详情；新建对象回列表 |
| 保存 | 成功后退出输入接收 | 校验后提交；失败保留草稿 | 对象详情并显示保存结果 |
| 发布/确认兑换 | 消费对应业务确认流程 | 执行业务确认与防重复规则 | 业务结果页 |

普通文本在返回或退出后不得继续修改旧字段。再次进入存在草稿的对象时提供“继续编辑/放弃修改”；草稿显示所属群和对象，不自动覆盖已被其他管理员更新的配置。草稿保存版本与正式版本不一致时提示冲突，并让用户选择重新载入或明确合并，禁止静默覆盖。

切群成功时原子解除旧 active_input、保留草稿并切换导航；切群失败保留原上下文。点击旧 A 群页面只恢复该页面，用户选择“继续编辑”后才重新激活 A 群输入。

默认草稿保留 7 天，属于本方案产品默认值；活动已结束、对象已删除或权限失效时，草稿可查看但不得直接提交。过期清理仅删除编辑草稿，不删除正式业务对象、订单或历史执行记录。

## 5. 基本可用性需求

### R01 命令和按钮分发可达

- /admin 绑定命令处理器；回调处理器按统一调用约定传参。
- 当前 35 个分发处理入口全部纳入契约验证；后续按注册清单自动增加覆盖。
- 未知 action、无法解析的旧格式、删除后的对象均显示原因与返回入口，不允许静默 return。
- 用真实 Application/Router 注册链验证从 Update 到真实处理器的路径，使用隔离 PostgreSQL，仅在 Telegram 传输边界注入模拟结果，不替换受验收的分发、目标群解析或实际持久化。
- 新菜单发布前必须验证全部展示按钮可以被注册处理器识别；含实体 ID 的按钮覆盖空、边界和失效对象。

### R02 操作反馈与恢复

按钮停止转圈仅表示收到操作，不代表保存或执行成功。完成反馈通过页面/消息呈现，不依赖第二次 callback answer。

| 情况 | 用户看到的结果 | 系统处理 |
|---|---|---|
| 保存成功且页面更新成功 | 已保存，以及最新值 | 记录配置版本和操作人 |
| 保存成功、页面更新失败 | 明确提示“已保存，请刷新查看”并提供重开入口 | 不重复提交业务写入 |
| 输入校验失败 | 字段原因与修正方式 | 保留输入和草稿 |
| 当前内容未变化 | 保持当前页面 | 不当作业务失败 |
| Telegram 明确拒绝 | 权限/内容错误等可理解说明 | 按业务记录失败，可修复后重新操作 |
| 发布或通知结果未知 | “结果待核实”，可查记录 | 禁止自动重发产生重复副作用 |
| 内部异常 | 简短错误说明、查询编号、返回入口 | 保存详细日志，不向用户直接输出内部异常字符串 |

如果私聊通道也不可达，无法保证立即通知用户；待处理结果须持久化，并在用户下次打开相关功能时显示。通知失败不改变已经提交的业务事实。

## 6. 公共组件与交互规范

### C01 显式开关与命令别名

“启用”设置为开启，“关闭”设置为关闭；重复点击当前值保持不变。标签按钮只展示说明，不更改状态。保存前读取当前版本，旧页面操作若会覆盖他人修改，先刷新并说明冲突。

命令别名校验格式、同群唯一性与保留命令冲突；无效输入不得当作成功清空。原命令和别名指向同一业务处理器，一条消息只执行一次。所有入口遵守同一命令开关；既有合法别名保持兼容，历史冲突须明确提示管理员修正。

### C02 统一列表

- 默认每页 8 条；这是交互默认值，不是平台限制。过长正文应缩略并在详情展开，不得以截断业务记录代替分页。
- 所有正文条目都有一一对应的详情入口。显示真实总数、当前页和可达的上一页/下一页，不写死“共 1 页”。
- 列表状态包含群、筛选、排序、页码或游标；详情返回恢复原状态。筛选变化回第一页。
- 空态提供“创建/添加”（角色允许时）、刷新和返回；查询失败保留相同出口。
- 删除末页唯一记录后回到合法页；新增记录导致列表变化时允许明确刷新，但不能永久漏掉旧记录。
- 优先迁移商城订单、彩蛋、老师/白名单、群选择；随后将现有业务列表全部纳入公共契约检查。
- 订单保留状态筛选并提供订单编号查找；查找仍校验群归属和查看权限。

### C03 消息、媒体与按钮编辑

在现有共享组件基础上提供统一编辑面板：正文、封面、按钮布局、预览、保存、返回。各业务通过适配器声明支持的字段和按钮类型；不支持的能力解释限制，不出现无效按钮。

按钮默认采用可视化逐项编辑。现有“文本|链接”和 JSON 输入保留为高级导入方式，统一调用公共解析与校验，不要求普通用户学习配置格式。链接按钮、自动回复触发按钮、底部操作按钮按业务能力保留区别，禁止为统一界面而丢失既有类型。

当前共享按钮编辑器的部分动作会直接写正式配置。本轮必须显式迁移为“编辑草稿 → 预览 → 保存”，确保返回和放弃修改的语义真实成立。简单功能启停继续即时生效，必须在页面标明，不能伪装成待保存字段。

预览复用发布内容的同一个渲染器，使用同一配置快照；仅允许添加“预览”说明，不修改正式对象、不向业务群发送、不扣分、不发放奖励。媒体/正文超长或格式不支持时，预览与发布提供同样的校验结果。

### C04 公共组件边界

| 公共能力 | 统一职责 | 业务适配器职责 |
|---|---|---|
| 导航 | 群上下文、返回来源、列表状态、旧入口归一 | 功能归属与页面内容 |
| 输入编辑 | 草稿、接收状态、保存/退出/放弃、冲突 | 字段规则与持久化 |
| 开关 | 显式目标值、重复点击、版本冲突 | 开关的业务作用与执行限制 |
| 列表 | 分页、空态、错误态、返回 | 查询条件、排序和条目摘要 |
| 消息编辑 | 媒体、正文、布局、预览一致性 | 业务变量与支持类型 |
| 操作反馈 | 收到/成功/失败/未知结果分离 | 业务结果、可恢复动作 |
| 权限 | 统一决策结果与原因 | 功能所需能力、对象归属 |

## 7. 业务流程补全

### B01 商城关闭限制

关闭商城后，文字指令、旧列表按钮、旧商品详情、旧确认按钮、自动回复触发入口都不得创建新兑换。检查必须进入兑换领域服务的事务边界，不能只在 UI 判断。

关闭与确认兑换并发时，以同一事务顺序决定：关闭先提交，则拒绝新兑换；订单先成功提交，则保留有效订单并按正常流程发放。关闭不删除既有订单，不阻止用户查看已创建订单，也不阻止有权限人员发放、取消或退款。

### B02 商品详情与确认兑换

~~~mermaid
flowchart LR
    A[商城列表] --> B[商品详情]
    B --> C[确认本次兑换]
    C --> D{执行前重新校验}
    D -->|通过| E[一次扣分并创建订单]
    D -->|不通过| F[解释原因并返回详情]
    E --> G[展示订单与发放状态]
~~~

商品详情展示名称、商品封面、兑换说明、所需积分、可用库存、个人限购、发放方式；商城总封面与商品封面分别使用。点击列表商品只打开详情。

点击“兑换”创建短时确认意图，绑定用户、群、商品、数量、价格及影响交易的商品版本。默认有效期 10 分钟。确认页展示本次扣分与预计剩余积分；真实扣分前重新校验，不承诺展示余额永久有效。

最终确认必须同时满足：商城开启、用户具备当前参与资格、商品属于目标群且在售、库存/限购/余额满足条件、确认意图未过期且未消费。价格或兑换条款发生变化时返回新详情并重新确认；不按旧展示价格静默成交。

重复点击同一确认、重复投递 Update、重启后重试均返回同一订单，不得重复扣分或重复减库存。用户再次购买必须创建新确认意图；不同意图之间仍执行并发库存和限购检查。扣分、库存、订单、意图消费在同一数据库事务完成。

旧 mall:redeem 按钮兼容为商品详情/重新确认，不能继续直接扣分。订单结果至少包含订单编号、商品、扣分、当前订单状态、发放方式和查看入口。

### B03 指定人员通知与人工发放

新订单形成时保存商品与发放人员快照。指定发放人员必须能在目标群内获得当前有效身份；角色撤销或离群后不可继续处理，订单转为管理员待处理事项，历史归属仍保留。

通知与权限规则：

| 接收者 | 内容与入口 | 无法送达时 |
|---|---|---|
| 购买者 | 订单编号、商品、扣分、待发放状态、自己的订单详情 | 下次打开商城可查看自己的订单，不重复扣分 |
| 指定发放人员 | 本群被分配订单、发放说明、标记发放入口 | 进入管理员待处理列表，显示通知失败/待核实 |
| 群管理员 | 未指定人员或通知异常的待处理订单 | 订单列表始终可查询并接管 |

指定人员在私聊得到“我的待发放订单”角色入口，仅可读取和处理分配给自己的目标群订单。身份在打开与提交时重新检查；其他人员不能通过转发按钮处理订单。退款/取消仍由既有管理员权限控制。

通知采用持久化投递记录。通知失败不回滚已成功订单，也不再次创建订单；明确失败可按策略重试，结果未知进入待核实，不自动重发。没有可达私聊的发放人员可通过群内简短指引打开 Bot；不在无关群广播订单信息。

管理员待处理通知默认发送到订单所属群，仅展示订单编号、待处理提示和受权限保护的入口，不公开买家详细资料。指定人员优先使用其可达私聊；通知不可达时同时保留角色入口与管理员队列。群通知失败也须记录，不将“进入队列”当作“通知已送达”。

沿用订单内部状态 created / fulfilled / canceled / refunded，界面分别显示“待发放 / 已人工标记发放 / 已取消 / 已退款”。标记发放需要确认并记录操作人、时间、说明；实际交付凭据可随说明保存。通知已送达不自动变更订单状态；人工标记本身不宣称购买者已实际收到物品。

商品调整发放人员不静默修改已有订单归属；管理员可对待发放订单显式改派并留审计。改派时取消旧人员尚未开始发送的通知，投递前重验责任人版本；已经发送或结果未知的记录保留真实结果，旧人员按钮按最新权限拒绝。用户订单与管理订单都能查看状态，商城关闭后仍可进入。

### B04 竞猜封面

活动封面进入创建草稿、预览和实际发布的同一内容快照。有封面时发布对应媒体与正文；无封面时保留文字消息。预览必须展示图片，不能只回到配置摘要。

本轮仅明确支持图片封面，包含按图片方式上传和既有支持的图片文件输入；其他类型显示清晰提示并保留草稿。替换、清空、返回后恢复、发布失败再进入均需保持一致。不得为媒体修复改变竞猜金额、结算与截止规则。

竞猜与拍卖的发布结果和活动可参与状态分开记录。发布成功或人工核实同一消息并完成关联前，活动不得因数据库已创建记录而开始接受下注/出价。结果未知保持待核实，不重新创建活动；核实时若已过截止时间，遵循原截止规则，不自动顺延。

### B05 拍卖图片输入

进入拍卖创建后，纯图片、带说明图片、纯文本均可进入同一草稿。没有 caption 的图片不得在读取编辑状态之前被过滤掉。

“其它消息”文案收敛为本轮明确支持的类型；不支持的文件/消息应说明原因并保留步骤。原“回复图片发送拍卖”的方式继续兼容。图片、说明与价格等必填项在发布前统一预览和检查，不提前发布半成品。

## 8. 工程实施约束

### A01 在现有基础上收敛

1. 保留现有功能域 Router、ConversationStateService、权限服务、PublishService 和按钮编辑能力，逐步收敛接口，不再新建平行框架。
2. 功能注册描述统一声明功能 ID、分类、权限、入口、动作、输入状态、业务适配器和验收场景；菜单与路由一致性由该清单校验。
3. UI 不直接执行数据库变更；共享组件不导入业务私有 handler；业务通过显式适配器调用公共能力。
4. 新迁移代码不用通配导入，关键路由/状态/订单边界不以动态 getattr 和全局覆盖掩盖接口不兼容。
5. 原协议由兼容适配层解析为统一请求。语义不清晰的旧写入按钮只打开新版页面，不推断并执行。
6. 新增表/字段必须更新 ORM、Alembic、Schema Gate 和数据库设计；不以启动临时 SQL 替代版本迁移。
7. 先恢复参数调用等关键类型检查在新边界的有效性，再逐步清理存量；不得用扩大禁用规则让检查变绿。

数据、兼容、操作审计及发布回退要求见配套[实施与运行恢复设计](../architecture/2026-10-10-service-repair-design.md)。

| T22 | B05 | 拍卖步骤提交纯图片、图文、文本、不支持类型 | 支持类型前进；不支持类型给出提示，不静默卡住 |

边界测试使用隔离数据库和模拟 Telegram；真实 Telegram 验收使用专用群、测试账号和测试积分。必须保留实际展示与业务结果证据，不能把 mock 发送成功作为现场验收。

### V02 功能完成状态与证据

每个功能分别登记：入口可达、配置持久化、执行消费、用户结果、失败恢复、权限/多群隔离。状态为“未核验 / 有缺口 / 本地验证通过 / Telegram 验收通过”；产品策略关闭与功能缺陷分开记录。

证据记录包含：需求/场景编号、代码提交、制品版本、验证时间、验证环境、群/用户/对象标识、预期与实际结果、可追溯的消息或执行记录。敏感标识在对外文档中脱敏，内部凭据按既有权限管理。

单个功能只有所有适用维度通过，才可标记对应范围完成；不适用必须说明理由。全部单元测试通过、健康检查通过、按钮存在、配置落库均不能单独支撑“全量闭环”。

## 11. 默认产品决策与后续边界

本方案已给出可实施默认值：六类导航、两列布局、列表每页 8 条、草稿保留 7 天、兑换确认 10 分钟、商城人工发放与独立通知状态。这些是设计决策，不是当前运行事实。

实施前需要确认的外部事实是当前线上代码/数据库版本、可用于验收的群和角色、指定人员的通知可达性；这些不影响本 PRD 的设计完整性。页面逐步替换，旧配置和业务对象继续有效；若无法证明某种旧写入按钮的安全语义，兼容为查看/重新确认。

本轮完成后，后续新增功能应先填写功能注册、交互和验收记录，再进入首页分类。禁止继续通过“先加按钮，后补处理”的方式对用户暴露尚无完整流程的能力。
